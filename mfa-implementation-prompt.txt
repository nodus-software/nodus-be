Goal
====

Provide a usable and secure MFA experience for users who may not always have access
to an authenticator-app TOTP code. The supported paths must be:

1. Authenticator-app TOTP.
2. Standards-compliant WebAuthn passkeys and roaming hardware security keys, used as
   a second factor after password verification (not passwordless authentication).
3. One-time offline recovery codes for emergency login.
4. An administrator-approved, fully audited MFA reset as the final recovery path.

Do not implement email OTP, SMS OTP, security questions, or an email-only recovery
bypass. Email may carry security notifications and a short-lived link created by an
authorized administrator, but possession of that email link must not be sufficient to
reset MFA: the user must also confirm their existing password.

Treat security and tenant isolation as acceptance criteria, not optional polish.

Current implementation problems to resolve
==========================================

Confirm these facts against the current code before editing:

- The backend recognizes MFA factor types "totp" and "biometric".
- "biometric" is a custom Ed25519 public-key/signature mechanism. It is not WebAuthn:
  it does not correctly validate the relying-party ID, origin, authenticator data,
  client data, user verification, credential counters, or a real WebAuthn ceremony.
- The frontend calls navigator.credentials but sends only credential raw IDs into the
  custom biometric API. Registration and login are therefore incompatible with the
  backend and must not be retained as a production authentication path.
- Backup codes already exist in mfa_backup_codes, but the login service accepts them
  by overloading method="totp". The frontend strips non-digits and only permits six
  characters, so users cannot actually enter the generated recovery-code format.
- TOTP setup currently creates backup codes before the TOTP factor is confirmed. Avoid
  leaving usable recovery credentials behind after an abandoned/failed enrollment.
- There is no recovery-code status/regeneration UI, no administrator MFA reset, and no
  viable sole-administrator recovery flow.
- My Account -> Security currently offers "Add authenticator app" and "Add biometric."
  Review this entire section and adjust its content, actions, states, and terminology.
- The biometric registration route and frontend onboarding auth mode are also
  inconsistent. Replace this path rather than patching the custom protocol.

Implementation order
====================

Implement in coherent stages so each stage is tested before the next:

1. Make recovery codes an explicit, usable login method and harden their lifecycle.
2. Replace the biometric implementation with real WebAuthn passkeys/security keys.
3. Add administrator-approved MFA reset and its recovery/enrollment flow.
4. Complete the frontend UX, documentation, migration/rollout instructions, and
   end-to-end verification.

1. Explicit recovery-code authentication
----------------------------------------

- Add "recovery_code" as an explicit login MFA method. It is an emergency
  authentication method, not an MFA factor displayed in the factor list.
- POST /auth/login must include "recovery_code" in mfa_methods only when the user has
  at least one unused recovery code. Do not reveal a count before password validation.
- POST /auth/login/mfa must accept:

    {
      "challenge_token": "...",
      "method": "recovery_code",
      "code": "..."
    }

- Normalize recovery-code input safely (for example, trim whitespace and accept the
  displayed separator/case convention), but do not apply TOTP's digits-only rules.
  Define one canonical representation before hashing and use it consistently for
  generation and verification.
- Preserve TOTP as method="totp" and stop accepting recovery codes through that method.
- Consume a recovery code atomically with consuming the login challenge and creating
  the authenticated session. A failed transaction must not burn the code, and concurrent
  attempts must not both succeed. Add the necessary conditional SQL/update semantics.
- Recovery-code failure must participate in the existing failed-attempt, lockout,
  generic-error, IP, and audit behavior. Never log or return submitted codes or hashes.
- Use cryptographically random, high-entropy, human-transcribable codes. Store only
  hashes. Do not weaken entropy merely for shorter UI text.

Recovery-code lifecycle APIs:

- Add an authenticated endpoint that reports only recovery-code status, including the
  number of unused codes. It must never return existing codes.
- Add an authenticated regeneration endpoint. Require the caller's current password in
  addition to their already MFA-authenticated session. In one transaction, invalidate
  all previous recovery codes and generate a complete replacement set. Return the new
  plaintext codes once, in that response only.
- Audit successful and failed regeneration without secrets. Notify the user by email
  after successful regeneration.
- Do not regenerate codes merely because another TOTP or passkey is added.
- Recovery codes should be created only after the user's first strong factor is
  successfully enrolled. For initial invitation, organization activation, reactivation,
  or MFA-reset enrollment, return the new codes once after factor confirmation and before
  consuming/completing the enrollment flow. Make factor confirmation, code creation, and
  enrollment-token consumption transactional so an interrupted flow is recoverable and
  does not create ambiguous credential state.
- If the current API shape makes that transaction impossible, refactor service ownership
  rather than coordinating security-sensitive writes non-atomically in HTTP handlers.

Use clear response DTOs. A reasonable contract is:

- GET /auth/mfa/recovery-codes/status
  -> { "remaining": 7, "generated": true }
- POST /auth/mfa/recovery-codes/regenerate
  body { "current_password": "..." }
  -> { "recovery_codes": ["..."], "remaining": 10 }

Keep the configured recovery-code count as the source of truth. Use the project's normal
success envelope and error conventions.

2. Standards-compliant WebAuthn
-------------------------------

- Remove the custom Ed25519 biometric verification and registration code. Replace the
  externally visible method/factor name "biometric" with "webauthn".
- Use the maintained github.com/go-webauthn/webauthn Go library (verify the current
  official API/version before integrating). Do not hand-roll attestation/assertion
  parsing or cryptographic verification.
- Configure explicit values for relying-party display name, RP ID, and allowed origins.
  Add validated environment/config fields and document production HTTPS requirements
  and intentional localhost development values. Do not infer security boundaries from
  untrusted Host or Origin headers.
- WebAuthn remains a second factor: password verification and the existing short-lived
  login challenge happen first. Do not add username-less or passwordless login.
- Support both platform authenticators/passkeys and cross-platform roaming security
  keys. Do not force a single attachment type. Require user verification. Use attestation
  conveyance "none" unless an existing documented policy requires managed attestation.
- Let the library choose/validate appropriate supported public-key algorithms; do not
  assume every authenticator supports only one algorithm.
- Store complete credential data needed by the library, including credential ID,
  public key, sign counter, transports/flags as applicable, user association, label,
  creation time, and tenant ownership. Credential IDs must be unique. Never store
  private keys.
- Persist WebAuthn ceremony/session data server-side so multiple application instances
  work correctly. Ceremony records must be tenant-bound, user-bound, purpose-bound
  (registration or authentication), short-lived, one-time-use, and safe against replay.
  Do not place trusted ceremony state solely in browser storage.
- Validate RP ID, allowed origin, challenge, ceremony purpose, credential ownership,
  user presence, required user verification, signature, and sign counter through the
  library. Handle possible cloned-authenticator/sign-counter warnings deliberately and
  audit the outcome without exposing credential material.
- Registration by a signed-in established user must require current-password
  confirmation to reduce the risk of a stolen session adding a new factor. Registration
  under a valid enrollment token does not require another password submission because
  the onboarding/reactivation/reset flow has already established it.
- Allow multiple WebAuthn credentials per user and require a user-supplied, trimmed,
  non-empty device label of reasonable length so credentials can be distinguished.
- Do not include credential IDs or detailed authenticator data in security logs.

Expose explicit ceremony endpoints rather than opaque strings. Use these routes unless
an existing route convention requires a narrowly justified equivalent:

- POST /auth/mfa/webauthn/register/options
  Auth: access session or enrollment token
  Established-session body: { "current_password": "...", "label": "..." }
  Enrollment body: { "label": "..." }
  Returns PublicKeyCredentialCreationOptions plus a server ceremony identifier.
- POST /auth/mfa/webauthn/register/verify
  Auth: same access session or enrollment token
  Body: ceremony identifier plus the complete browser registration credential.
  Returns the created MFA factor and, for first-factor enrollment only, the one-time
  recovery codes.
- POST /auth/login/mfa/webauthn/options
  Auth: none
  Body: { "challenge_token": "..." }
  Returns PublicKeyCredentialRequestOptions plus a server ceremony identifier.
- POST /auth/login/mfa/webauthn/verify
  Auth: none
  Body: login challenge token, ceremony identifier, and complete browser assertion.
  On success, atomically consumes both challenges, updates credential state, and returns
  the normal token pair.

Do not establish a session from the options endpoint. Apply the login challenge TTL and
single-use behavior to the WebAuthn flow, and do not let an options request extend the
original password-verified login window.

Legacy biometric migration and rollout:

- Add an up/down migration after the repository's current latest migration. Modify the
  database factor enum/check constraints and schema as needed for WebAuthn credentials
  and persisted ceremonies. Keep RLS enabled and forced, add tenant-isolation policies,
  tenant-stamping behavior, foreign keys, uniqueness, and expiry/query indexes consistent
  with existing tables.
- Legacy "biometric" records cannot be converted into WebAuthn credentials. Invalidate

- Before deletion, provide a documented read-only preflight query listing/counting users

- Remove obsolete Ed25519 imports, helpers, DTOs, routes, tests, and misleading comments.

3. Factor management invariants
-------------------------------

- Strong factors are confirmed TOTP factors and verified WebAuthn credentials.
  Recovery codes do not count as a strong factor.
- Permit at most one confirmed TOTP factor per user. Prevent duplicate pending TOTP
  setup records and cleanly replace/expire abandoned pending enrollment as appropriate.
- Permit multiple individually named WebAuthn credentials.
- Never allow a user to remove their last confirmed strong factor. Enforce this in the
  backend transactionally; frontend disabling is only a usability aid.
- Factor list responses must identify type, label, and created_at, but not secrets,
  public keys, credential IDs, counters, or ceremony data.
- Factor removal is security-sensitive. Require current-password confirmation for an
  established user's removal request, notify the user, and audit success/failure. Keep
  the existing endpoint only if its request semantics can be updated clearly in the
  OpenAPI contract; otherwise introduce an explicit removal action and migrate the
  frontend.
- Removing a WebAuthn credential must not delete unrelated credentials or recovery codes.
- TOTP secrets must remain encrypted at rest and must never appear after the initial
  setup response. Do not expose secrets in logs or errors.

4. Administrator-approved MFA reset
-----------------------------------

- Add a distinct permission code: users:mfa_reset. Include it in the permission catalog,
  migration, default superuser permission assignment behavior, frontend permission
  catalog, role editing UI, and OpenAPI documentation.
- Add an authenticated admin endpoint:

    POST /users/{userId}/mfa-reset
    Permission: users:mfa_reset
    Body: { "reason": "required non-empty operational reason" }
    Response: 202 Accepted (generic status; never return the raw token)

- Administrators must not reset their own MFA through this endpoint. This prevents an
  active stolen admin session from replacing its own factors. A tenant's sole admin is
  handled only through the controlled support runbook below.
- Reject invited, deactivated, or otherwise ineligible accounts with appropriate
  conflict responses. Do not silently reactivate or change the target user's status.
- On an approved request, create a random, hashed, single-use, short-lived MFA recovery
  token, invalidate earlier MFA-reset tokens for that user, revoke active sessions and
  refresh tokens, consume outstanding login challenges, and send the link to the user's
  already registered email. Do this transactionally where feasible; if mail delivery is
  outside the database transaction, follow the project's established secure mail/error
  pattern and make retries non-duplicative.
- Store tenant ID, target user, requesting administrator, hashed token, timestamps, and
  the stated reason. Apply forced RLS and tenant isolation.
- Add public endpoints comparable to the existing invitation/reactivation patterns:

    GET /users/mfa-recovery/{token}
    -> a minimal preview (name/organization if appropriate, expiry), without sensitive
       account or factor details

    POST /users/mfa-recovery/{token}/accept
    Body: { "current_password": "..." }
    -> { "enrollment_token": "..." }

- Acceptance must require the target user's existing password. Use timing-safe password
  verification and the normal lockout/security behavior where applicable. An email link
  alone must never reset MFA.
- Successful acceptance must atomically consume the reset token, delete/invalidate every
  prior MFA factor and recovery code, revoke sessions/tokens/challenges again, and issue
  a short-lived enrollment token restricted to enrolling a new strong factor. The user
  must not receive a normal session until the next normal password + MFA login.
- Audit request, rejection, mail outcome, preview abuse where appropriate, failed password
  confirmation, token expiry/replay, reset acceptance, factor enrollment, and subsequent
  login. Metadata should include actor/target/reason/method/outcome but no secrets.
- Send security notifications when a reset is requested and completed. Reuse the email
  template system and provide both HTML and plain-text templates.
- Apply strict endpoint rate limits and generic public errors that do not expose whether
  a user/token/account exists beyond what a valid token legitimately reveals.

Sole-administrator support runbook:

- Add a human-operated runbook for the case where the tenant's only administrator cannot
  authenticate and no other users possess users:mfa_reset.
- Require documented identity and organization-authority verification, a support ticket,
  two-person approval, exact tenant/user resolution, a database backup/recovery point,

- Prefer invoking the same application/service semantics through a narrowly scoped

- The procedure must revoke sessions, invalidate old factors/recovery codes, produce an

  account owner. Do not create a permanent support backdoor.

ACCEPTANCE CRITERIA
===================

The work is complete only when all of the following are true:

- A user can complete password + TOTP login.
- A user can complete password + real WebAuthn passkey/security-key login.
- A user with neither available can deliberately choose and consume one offline recovery
  code, after which that code cannot be reused.
- There is no email/SMS OTP or email-only authentication bypass.
- My Account accurately displays and manages TOTP, multiple passkeys/security keys, and
  recovery-code status, with current-password confirmation for sensitive mutations.
- New users and reactivated/recovered users can enroll either TOTP or WebAuthn, save their
  recovery codes once, and then log in normally.
- An authorized administrator can initiate a non-self MFA reset with a reason; the target
  must possess the email link and know the current password, then reenroll before login.
- Legacy custom biometric credentials are invalidated and no custom Ed25519 authentication
  path remains.
